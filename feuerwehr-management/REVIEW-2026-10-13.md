# Feuerwehr Management System (FENIX) – Umfassendes Review & Analyse

- **Datum:** 13. Oktober 2026  
- **Version:** 1.4.0  
- **Geprüfter Bereich:** Backend (`webapp/backend`), Frontend (`webapp/frontend`), Datenbank (`prisma/schema.prisma`), Deployment & Skripte (`deploy/`)

---

## 1. Gesamteindruck & Urteil

Die Webanwendung hinterlässt einen **sehr praxisnahen, soliden und modernen Gesamteindruck**. Sie wurde mit klarem Bezug zum echten Feuerwehrdienst (speziell am Profil des Löschbezirks 12 Wahlschied, Gemeinde Heusweiler) konzipiert und deckt die elementaren Kernprozesse (Personal-, Fahrzeug- und Geräteverwaltung, DGUV-Prüfbuch, Einsatzberichte mit Kräftenachweis nach FwDV, Brandsicherheitswachen) fundiert ab.

### Technologie-Stack
* **Frontend:** React 18, Vite 6, Tailwind CSS 4, TanStack Query v5, Zustand, React Router v7
* **Backend:** Node.js, Express, TypeScript, Prisma ORM 6, MySQL 8.4, Winston Logger
* **Sicherheits-Basis:** Das mit Version 1.4.0 durchgeführte Security-Hardening (In-Memory Access Tokens, gleitende httpOnly Refresh-Tokens, Whitelist gegen Mass Assignment in `body.ts`, Magic-Byte-Prüfung bei Uploads, relative Pfade in `files.ts`) ist überdurchschnittlich gut gelungen.

Gleichzeitig weist die Codebasis jedoch **gravierende funktionale Bugs, Altlasten aus der früheren Java-Desktop-Anwendung sowie klare architektonische Ausbaupotenziale** auf.

## 2. Kritische funktionale Befunde & Bugs

> [!CAUTION]
> Die folgenden Punkte beeinträchtigen die betriebliche und rechtliche Sicherheit im Feuerwehralltag und sollten vorrangig behoben werden.

### 🚨 2.1 Dashboard blendet überfällige Prüfungen und Untersuchungen aus
* **Fundstelle:** `webapp/backend/src/controllers/dashboard.controller.ts:39-58`
* **Problem:** Die Abfragen für Fahrzeug-TÜV/SP/Service, Geräteprüfungen und arbeitsmedizinische Vorsorgeuntersuchungen (G25, G26, G30) filtern mit `gte: new Date()`:
  ```typescript
  // Beispiel Fahrzeug-Prüfungen:
  where: {
    OR: [
      { tuevDate: { lte: reminderDate, gte: new Date() } },
      { spDate: { lte: reminderDate, gte: new Date() } },
      { serviceDate: { lte: reminderDate, gte: new Date() } },
    ],
  }
  ```
* **Auswirkung:** Es werden **ausschließlich zukünftige Termine der nächsten 30 Tage** abgefragt. Ein Termin in der Vergangenheit (`< new Date()`), der **bereits überfällig** ist, wird von der Datenbank komplett ausgefiltert! Obwohl der nachgelagerte Code `status: insp.tuevDate <= now ? 'red' : 'yellow'` implementiert hat, greift dies für echte Überfälligkeiten nie.
* **Risiko:** Abgelaufene Atemschutztauglichkeiten (G26.3) oder abgelaufener Fahrzeug-TÜV **verschwinden einfach vom Dashboard**, statt prominent rot als überfällig gewarnt zu werden.
* **Lösung:** `gte: new Date()` aus den `where`-Bedingungen entfernen, sodass alle Termine `<= reminderDate` (einschließlich aller historischen/überfälligen) abgefragt werden.

---

### 🚨 2.2 Stille Datenkappung im Kräftenachweis (Excel-Export)
* **Fundstelle:** `webapp/backend/src/services/report-generator.service.ts:531-553`
* **Problem:** Bei der Erzeugung des Kräftenachweises wird die Personalanzahl fest auf maximal 9 Personen limitiert:
  ```typescript
  for (let i = 0; i < Math.min(deployed.length, 9); i++) { ... }
  for (let i = 0; i < Math.min(reinforcement.length, 9); i++) { ... }
  ```
* **Auswirkung:** Sind an einem Einsatz oder an einer Sammelliste mehr als 9 Kräfte ausgerückt (z.B. bei Großschadenslagen oder wenn kein fahrzeugspezifischer Filter gesetzt ist), werden alle Einsatzkräfte ab Position 10 **stillschweigend verworfen**. Es erfolgt weder eine Fehlermeldung noch die Erzeugung eines Folgeblatts.

---

### 🚨 2.3 Funktionsloser E-Mail-Dienst
* **Fundstelle:** `webapp/backend/src/services/email.service.ts`
* **Problem:** Der Service implementiert SMTP-Versand und Erinnerungsvorlagen für Prüfungen und G-Untersuchungen. In der Datenbank existieren Flags wie `notifyTuev`, `notifyG26`, `notifyDue`.
* **Befund:** `emailService` wird **an keiner einzigen Stelle im gesamten Backend aufgerufen**. Es existiert kein Scheduler oder Hintergrundprozess. Die Checkboxen in der Benutzeroberfläche sind reine Attrappen ohne Funktion.

---

### 🚨 2.4 Monatsüberlauf-Fehler bei Prüfintervallen (Date Rollover)
* **Fundstellen:** `webapp/backend/src/controllers/inspection.controller.ts:253`, `webapp/backend/src/controllers/settings.controller.ts:593`, `webapp/frontend/src/components/inspections/CriteriaInspectionModal.tsx:98`
* **Problem:** Die nächste Fälligkeit wird per nativem JavaScript berechnet:
  ```typescript
  nextDueDate.setMonth(nextDueDate.getMonth() + intervalMonths);
  ```
  Erfolgt eine Prüfung an einem Monatsende (z.B. 31. August) bei einem 6-Monats-Intervall, versucht JavaScript den 31. Februar zu setzen und rollt automatisch auf den **2. oder 3. März** vor.
* **Lösung:** Das im Projekt bereits installierte Paket `date-fns` mit `addMonths()` nutzen.

---

### 🚨 2.5 Passwort-Lücke in Backup- & Restore-Skripten
* **Fundstelle:** `deploy/scripts/backup.sh:30-42`, `deploy/scripts/restore.sh:84-94`
* **Problem:** In beiden Shell-Skripten wird `DATABASE_URL` geparst, um `DB_USER`, `DB_HOST`, `DB_PORT` und `DB_NAME` zu ermitteln. **Das Datenbank-Passwort wird jedoch nicht extrahiert!**
* **Auswirkung:** Es verbleibt auf dem hartcodierten Fallback `DB_PASS="Ffw#VSLB12!25"`. Sobald für eine Instanz ein sicheres Passwort in `.env` vergeben wird, scheitern `mysqldump` und `restore` mit *Access Denied*. Außerdem packt `backup.sh:96` die `.env` unverschlüsselt und unmaskiert ins Archiv.

## 3. Architektonische Schwachstellen & Technische Schulden

### 3.1 Fehlende Mehrmandanten-/Standort-Abstraktion
* An zahlreichen Stellen ist der Löschbezirk 12 Wahlschied der Gemeinde Heusweiler hart in den Quelltext eingebrannt:
  * `webapp/frontend/src/pages/operations/OperationDetailPage.tsx:184`: Fester Dropdown-Eintrag `"Einheitenführer LB Wahlschied"`
  * `webapp/backend/src/services/report-generator.service.ts:245`: Beschaffungstext *"Gemeinde Heusweiler"*
  * `webapp/backend/src/services/report-generator.service.ts:278`: Dateinamenszusatz `'LB12'`
  * `webapp/backend/prisma/schema.prisma:492`: `designationLB @default("LB12")`
  * `webapp/frontend/src/components/layout/Sidebar.tsx:83`: Fester Logo-Pfad `/LB12.png`
* **Empfehlung:** Werte dynamisch aus der vorhandenen Tabelle `settings` (`fireStationName`, `fireStationCity`, `fireStationZip` etc.) auslesen.

### 3.2 76 Berechtigungs-Bits (`br0` bis `br75`)
* **Fundstelle:** `webapp/backend/prisma/schema.prisma:52-127`
* **Problem:** Relikt aus der dekompilierten Java-Applikation. Genutzt werden exakt 5 Bits (`br1` Fahrzeuge, `br2` Einsätze, `br3` Gerätewart, `br4` Veranstaltungen, `br5` Ausbildung).
* **Auswirkung:** 71 ungenutzte Boolean-Spalten blähen Datenbankzeilen, DMMF-Abgleiche und JWT/Session-Objekte unnötig auf.
* **Empfehlung:** Mittelfristige Migration auf ein Array an Befugnissen (z.B. `permissions: String[]` mit Strings wie `operations:write`, `equipment:manage`).

### 3.3 Vollständiges Fehlen von Datenbank-Indizes
* In `webapp/backend/prisma/schema.prisma` gibt es keinen einzigen manuellen `@@index`.
* Bei wachsendem Datenbestand führen Filter und Sortierungen zu Full-Table-Scans:
  * `operations`: `date`, `keyword`, `location`
  * `members`: `deletedAt`, `isInactive`, `lastName`
  * `article_inspections`: `articleId`, `inspectedAt`, `nextDueDate`
  * `refresh_tokens`: `expiresAt`

### 3.4 Fragiles Word-Templating über interne SDT-IDs
* **Fundstelle:** `webapp/backend/src/services/report-generator.service.ts:371-403`
* **Problem:** Checkboxen und Dropdowns werden anhand statischer interner Word-IDs manipuliert (z.B. `'688269389'`, `'1404645901'`).
* **Risiko:** Sobald die Vorlage `EinsatzberichtVorlageLB12.docx` in Microsoft Word geöffnet, angepasst und gespeichert wird, vergibt Word neue interne IDs. Die PDF-Erzeugung schlägt danach fehl oder Checkboxen bleiben leer.

### 3.5 Toter Code & Schema-Altlasten
* `model FireWatch` / Tabelle `fire_watches`: Wird im Frontend nicht verwendet, da Brandsicherheitswachen als `Event` mit Kategorie 3 abgebildet sind.
* `tenantId` existiert auf diversen Tabellen, wird aber nirgends befüllt oder ausgewertet.
* Tabelle `operation_reports` wird seit Wegfall des Freitext-Tabs in 1.4.0 nicht mehr genutzt.
* Die Projekt-Root-`README.md` verweist noch auf Maven und dekompilierten Java-Quellcode.

## 5. DevOps, Docker & Betriebssicherheit

1. **LibreOffice im Docker-Image nachrüsten:**
   * In `deploy/docker/backend.Dockerfile:18-20` fehlt `libreoffice`. Im Docker-Container schlägt daher jede PDF-Konvertierung fehl und das System liefert immer nur `.docx`/`.xlsx` aus.
2. **Docker-Entrypoint anpassen:**
   * In `deploy/docker/backend-entrypoint.sh:9` wird noch `prisma db push` ausgeführt. Dies sollte wie in den nativen Update-Skripten durch idempotente SQL-Migrationen ersetzt werden.
3. **Automatischer Token-Cleanup:**
   * In `webapp/backend/src/services/auth.service.ts` werden abgelaufene Refresh-Tokens nur beim Login des jeweiligen Benutzers gelöscht. Ein nächtlicher Aufräumjob für `refresh_tokens` verhindert unbegrenztes Tabellenwachstum.
